# 工程效率

本次优化保持网络结构、权重布局、JPEG95 像素处理、30Hz 最近 PTS 采样、halo、重复采样权重、损失公式及事件匹配目标。没有引入磁盘缓存、哈希、精度开关或新的依赖。

## 数据与执行

`WindowSampler` 每视频构造一次逻辑时间轴、最近原生帧索引和重复计数。窗口使用二分边界与切片，不再逐窗扫描或重建整个时间轴。独立调用的 `sample_window` 接口仍可用，训练和推理使用可复用的 sampler。

`FrameReader` 保留当前视频解码器，用有容量上限的 LRU 缓存复用已完成 resize/JPEG95/RGB 转换的帧。相邻窗口顺序推进；切换视频、回退或远距离跳跃时 seek。重复索引只处理一次，再按原请求顺序组装。缓存满时逐帧淘汰，不缓存整个数据集。

读取线程仅预取下一窗口。模型执行、优化器更新及训练随机数操作保持在主线程，结束上下文时等待读取线程退出再关闭解码器。随机训练顺序保持不变；访问间隔超过缓存容量的帧仍需要重新解码。这是有限内存下的取舍，不能用重排训练样本消除。

训练目标按原生帧预计算，通过有序事件最近邻查找替代逐窗口的全事件距离矩阵。类别平衡不再按 epoch 重复，恢复使用已有的完整配置比较后复用统计。保持完整请求顺序和 PTS 的 checkpoint 格式，以保留现有恢复契约。

CUDA 训练的损失分母仍使用原设备逐窗口归约：重复采样的 `1/3` 等权重在 CPU 和 CUDA 上可能因求和顺序得到不同末位。只合并这些标量结果的回传，再按原顺序执行 Python 求和；不能用 CPU 归约替代。非有限损失在每次参数更新前统一检查，公开的 `loss_sums` 接口仍即时检查。

推理边运行边累加原生帧 logits，完成后平均和插值，不保留全部窗口和输出。JSON 流式写入临时文件再替换目标，避免整份字符串副本，失败时保持已有输出。

输入归一化仍使用 FP32，在新建浮点张量上原地运算以减少临时副本。首轮等价优化保留原推理 FP32；后续 CUDA 推理精度调整与完整指标验证见下文。完整网络的峰值显存仍可能由卷积激活主导。

## 事件评价

峰值检测向量化，NMS 用帧轴占用标记查询邻域。匹配先按容差关系分成独立组件，再使用滚动分数和紧凑回溯；仍先最大化命中数，再最小化误差，并保持旧版平局顺序。整体和来源报告复用每视频的匹配统计。

阈值搜索只需要匹配数量，因此使用有序双指针计算最大匹配数；需要误差及匹配对的正式评价继续使用完整匹配语义。

## 验证与测量

回归覆盖真实视频的重叠、倒序、重复与晚段读取，非均匀 PTS 和不同采样率，增量 logits 还原，匹配平局、连续/恢复训练，以及预取顺序与异常清理。验证入口为项目环境中的 `PYTHONPATH=src python -m pytest -q`。

2026-11-10 在 RTX 5070 Ti Laptop GPU 上，将本次修改与修改前 HEAD 对照：FFmpeg `testsrc2` 生成 1280×720、30fps、6.8 秒的 H.264 视频（GOP 60、2 个 B 帧），使用仓库 `weights/best.pt`、完整 448×796 输入、FP32 推理。PyTorch 4 个 CPU 线程、OpenCV 1 个线程；两版各执行两次。

204 个原生帧形成 3 个窗口、292 个逻辑输入槽。旧版打开视频 3 次并执行 292 次 JPEG 编码，新版打开 1 次并执行 204 次 JPEG 编码。四次结果的逐帧分数逐值完全相等，最大差异为 0，事件列表相同。

旧版两次墙钟时间为 6.19 / 3.97 秒，新版为 3.32 / 2.72 秒。预热后的对照约减少 32% 时间；样本很小，存在初始化与设备状态影响，不代表真实比赛数据的平均提速。两版整网峰值已分配显存都约 6.70 GB，没有观察到整体峰值下降。

独立微基准中，共享 sampler 的单窗口调用在 60 秒和 3600 秒时间轴上都约 7.5 微秒；900 对稀疏事件的匹配从约 0.306 秒降至 0.0031 秒。这些数字只描述对应子步骤，不能相乘或换算为整体训练加速。

另以真实网络、完整 448×796 输入、BF16、`backbone2` 和 12 帧/10fps H.264 视频执行三次更新。固定 seed 并启用 CUDA 确定性设置后，新旧实现的模型、AdamW 状态、随机数状态、请求顺序和配置完全相等；新版连续训练、新版暂停恢复以及接续旧版 checkpoint 也完全相等。此短例主要验证数值与恢复语义，预热后两版总耗时均约 1 秒，不用于宣称训练吞吐提升。

最终完整测试为 41 项通过，包含 CUDA 分母归约回归；仅有上游 `torch.jit.script` 弃用提示。

没有使用未经测量的收益承诺。首轮等价优化没有修改精度、删除 JPEG95、减少上下文或缓存训练中的中间网络特征。后续在用户允许小幅指标变化后单独验证精度调整；JPEG95、上下文和训练语义继续保留。

`scripts/benchmark_inference.py` 在独立进程中交错执行基线与当前 CLI，计入启动、模型加载、PTS 扫描、推理、JSON 写盘和进程退出。输入为六个真实来源：自采20fps的16秒、admin和back各12秒无重编码截取，以及完整的 E2E（317帧）、Loveall（74帧）、TrackNet（207帧）视频；当前机器 RTX 5070 Ti Laptop，PyTorch 4线程，OpenCV保持环境默认线程数。双方预热后各运行三轮；没有同时执行其他解码或GPU测试。

六视频整轮外部墙钟中位数从 **59.026秒降到57.087秒**，吞吐约 **1.034倍**，耗时减少约 **3.3%**；当前最慢轮57.444秒仍快于基线最快轮58.618秒，各来源中位数均改善。所有运行的完整分数、PTS、事件和阈值逐值相等。峰值已分配显存均为7,871,408,128字节，未观察到整网峰值下降。44项回归通过。

该结果是新视频完整命令的测量，不把输入阶段微基准或首个单视频结果当整体加速。原始本机报告在 `runs/inference-benchmark/layout-comparison.json`，输入清单在同目录 `videos.json`；这些运行数据不提交Git。

## 新视频推理：去除时间戳解码扫描

`probe_video` 改用 `ffprobe -show_packets` 读取整数 PTS，按显示顺序排序并乘原来的 `float(time_base)`。B帧的包顺序不等于显示顺序；无重编码剪辑保留的解码预滚包带 `DISCARD` 标记，必须排除，不能加入输出帧轴。OpenCV仍负责实际图像解码，JPEG95像素协议保持不变。没有引入PyAV依赖或新的流式窗口实现。

对原项目全部 **3,762视频／1,665,243帧**逐项比较原有FP64时间数组，**0处差异**。报告在 `runs/inference-benchmark/packet-pts-all.json`。新增真实FFmpeg构造回归覆盖H.264、HEVC、MPEG4、MP4/MOV、B帧重排、非零起点、变帧率及带discard预滚的流复制剪辑。四个构造视频另通过完整CUDA模型对照：全部90帧的分数、时间轴和事件与`9333c67`完全相同；报告在`runs/inference-benchmark/edge-parity.json`。完整回归为48项通过。

四个完整真实视频的交错CPU探针中，旧frame扫描到新packet扫描的中位耗时分别为：20fps/3600帧 **2.823→0.079秒**，25fps/395帧 **1.909→0.068秒**，29.97fps/341帧 **1.266→0.066秒**，非均匀PTS的13956帧MOV **34.636→0.211秒**。这些探针保留在本次工具转录，描述扫描阶段，不冒充整段推理提速。

RGB通道转换也从NumPy负步长切片复制改为`cv2.cvtColor(BGR2RGB)`，保持uint8像素不变。本机448×796图像的100次交错微测中位为1.200→0.074毫秒/帧；这项收益仍需由完整命令测量确认，不能与扫描或布局的倍数相乘。

FFmpeg对packet与frame的区别见[ffprobe文档](https://ffmpeg.org/ffprobe.html)，预滚discard的语义见[AVPacket标记定义](https://ffmpeg.org/doxygen/9.0/group__lavc__packet.html)。本轮未扩展到缺失packet PTS的损坏容器或额外编码格式。

随后在相同六来源清单上重新交错测量三轮：`9333c67`整轮完整命令中位 **54.821秒**，包含布局、packet扫描和通道转换的`4bfeb81`为 **49.027秒**，吞吐 **1.118倍**，耗时减少约 **10.6%**。当前最慢轮49.100秒快于基线最快轮53.813秒；六来源中位均改善（约1.072–1.201倍），所有完整输出仍逐值相等，峰值显存仍约7.87GB。报告为`runs/inference-benchmark/packet-color-comparison.json`。不同轮次宿主状态会变化，因此仅比较同轮交错结果，不用前一轮59秒基线与本轮49秒拼接成更大的加速比例。

## 完整指标约束下的数值候选

后续验收允许逐帧分数变化，保持原权重、JPEG95、采样、上下文和两套阈值，比较完整事件指标。`scripts/compare_precision.py` 报告总体、击球/落地及各来源的 TP/FP/FN、Precision/Recall/F1、平均定位帧误差和每分钟误报数。原项目的冻结 EO 预测覆盖 validation 505、holdout 45、official 1622、admin 6，共 948,269 帧；复用这些原始预测重新评价，60 个已发布计数单元全部匹配。外部集的 P/R/F1 也完全一致，FP/min 最大仅有浮点末位差异。基准文件在 `runs/inference-benchmark/reference-scores`，来源记录和报告分别为 `provenance.json`、`../reference-report/report.json`。

validation 原始文件取 `logits["event_only_phase0"]`，按 `sigmoid(eventness) * softmax(type)` 合成两列分数；external 原始文件已有两列分数。时间轴逐视频与冻结元数据核对。GT 只保留 hit/bounce，遵循原正式评价器，排除 net。原记录没有明确保存 TF32 后端开关，因此报告明确标注历史预测基线，不声称它与当前禁用 TF32 的 FP32 逐位一致。候选仍须从所有原视频重新推理。

候选包含显式的 83 组 Conv3d/BatchNorm3d 推理融合，以及仅作用于视觉主干的 FP16；局部状态、GRU 和输出头仍为 FP32。普通 `load_model` 的 583 项 state dict 和训练路径保持原样。完整质量结果见下文；生产路径通过 `predict_video` 统一使用融合，CUDA 选择 FP16 视觉主干，CPU 保持 FP32。CLI 先在 CPU 加载和融合，再搬到目标设备。

标准 156 槽真实窗口的独立进程微测中，原 FP32、TF32、融合 FP32、融合 FP16 的前向中位数分别为 0.479、0.517、0.424、0.364 秒。融合 FP16 峰值约 4.70GB，原 FP32 约 7.87GB。这些仅为前向结果，不能作为完整命令加速比例。独立进程的 channels-last 候选仍明显更慢，未采用；97 个 ReLU/SiLU 改原地执行虽在三个真实窗口的全部五类输出上逐位一致，但没有速度或峰值显存收益，也未采用。原始报告位于 `runs/inference-benchmark/isolated-forward/` 和 `inplace-probe.json`。

微测必须防止显存缓存干扰：本机 WSL2 上，交替运行不同长度的 FP32/FP16 后，闲置缓存曾占满显存，使同一 156 槽前向从约 0.47 秒变成 31.56 秒。仅释放闲置缓存就恢复正常；层级计时定位到第一个高分辨率点卷积。后续模式测速采用独立进程，完整质量运行只计算选定候选并读取历史基线，避免将这种实验资源干扰误认为算子优化效果。未向产品添加通用 allocator 配置或逐窗清缓存操作。

## 固定模型结构与启动成本

视觉骨干改为本地固定的原生 PyTorch X3D-S，去掉运行时对 PyTorchVideo、torchvision 和 fvcore 的依赖。没有改变网络层、权重键或计算顺序；保留原构造器中临时分类头及第二次初始化，是为了保持新建模型后的随机数状态和训练初始化行为。来源许可保留在 `LICENSES/`。

三个随机种子的全部583项状态、332个参数及其顺序、457个模块名称和类型名称、构造后的随机数状态均与原实现一致。真实CUDA窗口在FP32、BF16、FP16及融合FP16路径上，全部五种输出逐值相等；六个完整来源视频经过候选生产推理路径的分数和PTS也完全一致。报告在 `runs/inference-benchmark/native-gpu-parity.json`。回归测试另保留由旧实现生成的数值fixture，覆盖加载checkpoint后的真实前向语义。

五轮ABBA、双方各10个全新Python进程，仅执行模型模块导入后退出，外部墙钟中位数从 **3.895秒降至2.214秒**，减少 **1.681秒**。计时包含解释器启动、模块导入、结果打印及退出，并非纯import内部计时，也不是完整视频推理提速。该实验报告为 `runs/inference-benchmark/native-import-abba.json`；最终收益仍以完整CLI对照为准。

另测试了meta设备构造再赋checkpoint：正常加载耗时0.122–0.136秒，meta路径0.830–0.832秒，冷启动反而更慢，因此未采用。
